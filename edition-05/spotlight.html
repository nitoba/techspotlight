⚡ feature #12677 procedure Form Dinâmico reaproveitamento-respostas.sql
Reaproveitamento de respostas — menos retrabalho entre diagnósticos
❌ problema
Quando um novo diagnóstico era criado, muitas respostas já existiam em diagnósticos ou safras anteriores. O usuário precisava refazer trabalho, mas uma cópia simples também era perigosa: podia duplicar respostas, reaproveitar perguntas erradas ou perder rastreabilidade.
✓ o que entregamos
→ #12677 Configuração de reaproveitamento no CMS
→ Controle de elegibilidade nos níveis do diagnóstico
→ Tela em Operações > Diagnóstico para origem, destino, propriedades e nova data
→ Endpoint backend para executar o reaproveitamento
→ Procedure + migration para copiar apenas respostas elegíveis
→ Motivos detalhados para respostas ignoradas
→ Ajustes de performance, status dos atendimentos e cálculo de ranking
🎯 destaque técnico
O reaproveitamento não copia tudo. Ele avalia elegibilidade, identifica respostas duplicadas, existentes ou sem correspondência, registra o motivo das ignoradas e atualiza o ranking para múltiplos atendimentos. O ganho é operacional sem abrir mão de consistência.

📊 feature #12529 performance procedure importacao-generica.service.ts
Importação genérica — de 27 minutos para 5 segundos
❌ problema
A importação de produtores e propriedades estava dependente de fluxos muito específicos. Cada nova planilha exigia regra própria, normalização no serviço e pouca rastreabilidade do que aconteceu em cada linha. Além disso, o processamento era lento: em um cenário real, chegava perto de 27 minutos.
✓ o que entregamos
→ #12529 Fluxo genérico de importação configurável por categoria
→ Normalização movida para o banco, usando staging + procedure
→ Tela genérica com download de modelo, parâmetros dinâmicos, upload e execução
→ Histórico de execução com linhas processadas e linhas com problema
→ Visibilidade por certificadora e permissão do usuário
→ Configuração no CMS para campos, parâmetros e categoria da importação
→ Resultado principal: processamento caiu de ~27min para ~5s
🎯 destaque técnico
A decisão foi tirar a normalização pesada do serviço dedicado e transformar importação em motor de execução: configuração define os campos, staging recebe os dados e a procedure resolve o trabalho pesado no banco. Menos código específico e muito mais performance.
// pipeline da importação
CONFIG
campos, parâmetros e categoria
UPLOAD
planilha + parâmetros dinâmicos
STAGING
linhas brutas e validação
PROCEDURE
normalização no banco
HISTÓRICO
execução, detalhe e erros por linha
PERMISSÕES
certificadora e perfil do usuário
resultado: ~27min → ~5s em processamento de importação
impacto
"O ganho não foi só deixar a tela mais genérica. Foi transformar um fluxo lento e específico em um motor configurável, rastreável e rápido."

⚡ Lightning #12348 Sentinel-2 NDVI sicar-inspecao-vegetacao.service.ts
Inspeção de vegetação em APP via NDVI Sentinel-2
o que entregamos
→ SicarInspecaoVegetacaoService — orquestração da análise (selecionar cena, processar, gerar preview)
→ SentinelStacClient — busca cenas Sentinel-2 L2A no STAC
→ Cálculo de estatísticas NDVI sobre a geometria da APP
→ Preview PNG gerado server-side + cache via anexo da propriedade
→ html2canvas para relatórios contextuais com mapa + dados
→ Endpoints: solicitação, listagem, processamento, preview, histórico
→ SicarDataProcessorService — integridade de referências (temas/status/tipos)
por que importa
Quando uma propriedade declara APP preservada, agora dá pra auditar isso direto do satélite, sem ter ido no campo. O NDVI das cenas Sentinel-2 mostra cobertura vegetal na própria geometria da APP — e o histórico fica anexado à propriedade pra consulta futura.

async inspect(carId: number) {
  const geom = await this.loadAppGeometry(carId)
  const scenes = await stac.searchL2A(geom)
  const stats = await this.computeNDVI(scenes, geom)
  const png = await this.renderPreview(stats)
  await this.cacheAsAttachment(carId, png)
  return { stats, png }
}

🔐 feature #11404 MFA better-auth.guard.ts
Better-Auth — Auth V2 com MFA e tokens parciais
❌ problema
O fluxo antigo de autenticação precisava evoluir sem quebrar o uso atual. O desafio era introduzir uma base nova, com MFA, TOTP, ativação de conta, compatibilidade com fluxos legados e segurança no momento mais sensível: antes da emissão do token completo.
✓ o que entregamos
→ #11404 Estrutura base do Better-Auth com tabelas core
→ Entidades account, session, user e verification
→ Auth V2 integrado ao módulo principal de autenticação
→ Tokens parciais para login pendente de MFA
→ Fluxos MFA Email/Google/TOTP com UI modernizada
→ Locks transacionais para senha e ativação de conta
→ Ajustes em guards, decorators, apikeys e endpoints de validação
🎯 destaque técnico
O ponto central é impedir que um usuário receba acesso completo antes de concluir a verificação. O token parcial carrega apenas o estado necessário para terminar o MFA; só depois disso o fluxo emite o token final.
